## Ответы на контрольные вопросы

**1. Что такое горизонтальное масштабирование?**
Добавление новых экземпляров (реплик) приложения на отдельных серверах/контейнерах для распределения нагрузки.

**2. Чем оно отличается от вертикального масштабирования?**
Вертикальное — увеличение мощности одного сервера (больше CPU/RAM). Горизонтальное — увеличение количества серверов (более гибкое, но требует балансировки).

**3. Зачем нужен load balancer?**
Распределяет входящие запросы между несколькими репликами приложения и скрывает от клиента внутреннюю структуру кластера.

**4. Какую роль в этой работе выполняет NGINX?**
Выступает в роли reverse proxy и load balancer, принимая все запросы от клиентов и распределяя их между репликами Go-сервиса.

**5. Что такое upstream в NGINX?**
Блок конфигурации, который описывает группу бэкенд-серверов (реплик), между которыми NGINX распределяет трафик.

**6. Почему для горизонтального масштабирования желательно делать сервис stateless?**
Stateless-сервис не хранит данные пользователя локально — любой запрос может пойти на любую реплику. Иначе нужно синхронизировать состояние между репликами (сессии, кэш).

**7. Зачем нужен health endpoint?**
Для проверки работоспособности реплики (например, `/health`). Load balancer периодически опрашивает его и исключает нездоровые реплики из ротации.

**8. Почему полезно добавлять X-Instance-ID?**
Чтобы в логах и метриках понимать, какая именно реплика обработала запрос — критически важно при отладке распределённой системы.

**9. Что происходит при остановке одной из реплик?**
Load balancer перестаёт направлять запросы на эту реплику (после неудачных health-чеков), остальные реплики продолжают работать. Сервис сохраняет доступность.

**10. Почему клиенту удобнее работать с одной точкой входа, а не с несколькими адресами реплик?**
Клиент не должен знать о внутренней архитектуре — ему нужен один стабильный адрес. Load balancer обеспечивает отказоустойчивость (переживает отказ реплик) и балансировку без изменения клиента.
